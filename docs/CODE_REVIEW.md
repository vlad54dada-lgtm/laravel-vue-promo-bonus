# Частина 2 — Рев'ю коду

Рев'ю фрагмента «нарахувати бонус на баланс гравця» (роут + `WalletController::creditBonus` + фрагмент Vue-компонента). Формат — як коментар до PR колеги.

> Твердження про поведінку PHP/Laravel перевірені емпірично на PHP 8.4.24 (Laravel 12): арифметика `+=` з різними входами, склад middleware-груп фреймворку і дефолтні заголовки відповіді. Позначки «(перевірено)» стосуються саме цих прогонів.

## Загальний вердикт

У поточному вигляді це не «фіча з шорсткостями», а пряма діра для маніпуляції грошима: **будь-хто без автентифікації може змінити баланс будь-якого гравця на довільну суму (включно з від'ємною) одним GET-запитом**. Мержити не можна; нижче — 15 зауважень за пріоритетом.

## Критичне (блокери)

**1. Немає ані автентифікації, ані авторизації.**
Роут не під `auth`-middleware — доступний аноніму. Гравець береться з URL (`{player}`), а не з токена. Це класичний IDOR: перебором `player_id` можна нарахувати (або від'ємним значенням — списати, див. п. 3) кошти будь-кому. За вимогами домену гравець має визначатися **з токена автентифікації**, а нарахування бонусу взагалі не повинно бути дією, яку клієнт викликає на довільну суму, — це або службова (адмінська) операція, або наслідок бізнес-події (промокод, депозит-бонус), де суму визначає сервер.

**2. `amount` не валідується — і суму диктує клієнт.** (перевірено на PHP 8.4)
- `amount` відсутній → `$request->amount` = `null` → `balance += null` дає **той самий баланс, без помилки**: «успішна» операція 200 OK без ефекту.
- Від'ємний `amount` → `balance += -30` дає **70**: ендпоінт «нарахування» фактично **списує** кошти GET-запитом.
- Нечислове значення (`abc`) або порожнє (`?amount=`) → `balance += "abc"` кидає **`TypeError: Unsupported operand types` → HTTP 500** (у PHP 8 це жорстка помилка, а не тихий нуль, як було в PHP 7).
- Провідно-числовий рядок (`50abc`) → **150** з `Warning: A non-numeric value encountered` (тихе приведення до 50).
- Верхньої межі немає: `?amount=999999999999` нарахує майже трильйон.
Навіть із валідацією лишається концептуальна помилка: суму бонусу має визначати сервер за бізнес-правилом, а не приймати з запиту.

**3. Мутація стану через GET.**
`Route::get('/players/{player}/credit-bonus', ...)` змінює баланс. GET префетчиться браузером, «відкривається» прев'ю месенджерів (бонус нарахується без наміру користувача), потрапляє з усіма параметрами в access-логи та історію браузера. Тег `<img src="…/credit-bonus?amount=100000">` на будь-якому сайті виконає операцію.
Уточнення, щоб не вводити рев'ю в оману: тут це працює **не тому, що «GET обходить CSRF»**. На API-роути (`routes/api.php`) CSRF-middleware Laravel не поширюється взагалі — ані на GET, ані на POST: `ValidateCsrfToken` входить лише у групу `web` (перевірено в `Foundation/Configuration/Middleware.php`), а дефолтна група `api` — це фактично лише `SubstituteBindings` (throttle у ній умовний і без явного `throttleApi()` не вмикається — що узгоджується з п. 9 нижче). Тег `<img>` спрацьовує просто тому, що ендпоінт відкритий без автентифікації (п. 1). Перехід на `POST` потрібен за семантикою HTTP і прибирає вектори prefetch/прев'ю/логів, але сам по собі захисту не додає — від cross-site запитів тут захищає Bearer-автентифікація (Sanctum), токен якої браузер не відправляє автоматично. Кешування відповіді малоймовірне (Laravel за замовчуванням віддає `Cache-Control: no-cache, private` — перевірено), але покладатися на дефолтний заголовок для грошової операції не можна.

**4. Race condition: read-modify-write без транзакції та блокування.**
`$player->balance += …; $player->save()` — між читанням (route model binding) і записом інший запит може змінити баланс → lost update. Два паралельні нарахування по 100 можуть дати +100 замість +200. Потрібно: `DB::transaction` + `lockForUpdate()` (або атомарний `increment()`), плюс **ідемпотентність** — унікальний ключ операції, щоб мережевий ретрай не нарахував бонус двічі. Для гемблінг-домену це основна вимога, не «nice to have».

**5. Гроші через float-арифметику.** (перевірено)
`$request->amount` — рядок з HTTP; після приведення це float зі стандартними помилками подвійної точності: `0.1 + 0.2` дає `0.30000000000000004`. Баланс має зберігатися в integer мінорних одиницях (центах) або оброблятися через decimal/bcmath — але не через `+=` з сирим інпутом. Окремий шар тієї самої проблеми — формат «на дроті»: відповідь віддає баланс голим JSON-числом, а фронтенд кладе його в JS `Number` (той самий IEEE-754 double). Контракт має явно фіксувати одиниці: integer-центи або decimal-рядок.

## Серйозне

**6. Витік фінансових даних: баланс будь-якого гравця читається будь-ким.**
Відповідь завжди містить `balance`, а `amount` необов'язковий (`+= null` нічого не змінює) — отже `GET /api/players/{id}/credit-bonus` без параметрів працює як **неавтентифікований read-oracle** поточного балансу довільного гравця (перебором id). Навіть якби мутацію заборонили, витік лишився б. Баланс має бачити лише сам гравець через автентифікований ендпоінт.

**7. Немає журналу операцій (ledger).**
Баланс змінюється «в лоб», без запису хто/коли/за що/скільки. Неможливо аудитувати, звіряти, розслідувати інцидент чи скасувати помилкове нарахування. Для платформи з реальними грошима зміна балансу без ledger-запису недопустима.

**8. Немає обробки помилок і статусів відповіді.**
Відповідь завжди `200 {success: true}` — контракт не передбачає ані 422, ані 4xx для доменних відмов. `save()` може кинути виняток — не обробляється.

**9. Немає rate limiting** — нарахування можна викликати в циклі без обмежень.

**10. Архітектурно: логіка в контролері.**
Немає FormRequest, немає сервісного шару, `$request->amount` замість `$request->validated()`. Для грошової операції — мінімум сервіс + типізовані доменні помилки.

**11. Інваріанти балансу ніяк не закріплені на рівні БД.**
Немає `CHECK (balance >= 0)` / unsigned, немає гарантії достатнього діапазону колонки. Наслідок необмеженого `amount` (п. 2): переповнення колонки — у non-strict MySQL це **тихе урізання значення до максимуму** (мовчазне псування балансу), у strict — 500. Грошові інваріанти мають стояти і в схемі, як друга лінія оборони за кодом.

**12. Немає тестів на грошову операцію.**
Для PR, що змінює баланс, це блокер сам по собі: потрібні feature-тести на негативні/граничні `amount` (null / 0 / від'ємне / `abc` / переповнення), на контракт помилок (не завжди-200) і на конкурентність з ідемпотентністю (два паралельні нарахування → рівно +200; ретрай — рівно один запис).

## Фронтенд

**13. `axios.get` з `params` для грошової мутації** — дзеркалить проблему № 3; після виправлення бекенда має стати `axios.post` з тілом.

**14. `this.player.id` у URL** — клієнт сам каже, кому нараховувати; після виправлення № 1 ідентифікатор гравця з фронтенда взагалі зникає (сервер бере його з токена).

**15. Немає обробки помилок і стану завантаження.**
`await` без `try/catch` — відхилений проміс (напр., 500 від `TypeError` з п. 2) впаде необробленим, користувач не побачить причину. Немає прапорця loading/disabled — подвійний клік = подвійний запит = подвійне нарахування (у зв'язці з № 4). Баланс перезаписується відповіддю без урахування, що запит міг задублюватися.

## Дрібніше

- Поки роут відкритий, різниця відповідей 404 vs 200 на `{player}` дозволяє перебором з'ясовувати, які player_id існують (enumeration) — лікується тим самим auth з п. 1.
- Назва `creditBonus` у `WalletController` натякає, що поруч з'являться інші грошові операції — тим більше потрібен сервіс/ledger, а не інкремент поля в контролері.

## Як мав би виглядати підхід (ескіз)

```php
// POST /api/bonus/claim  (auth:sanctum, throttle)
public function claim(ClaimBonusRequest $request, BonusService $service)
{
    // гравець — тільки з токена; суму визначає сервер за бізнес-правилом
    $result = $service->credit($request->user(), $request->validated('reason_id'));
    return BonusResource::make($result); // 422/409 — через доменні винятки
}

// BonusService::credit — DB::transaction + lockForUpdate + унікальний
// ключ ідемпотентності + запис у wallet_transactions (integer-центи)
```

Саме так побудований основний код цього репозиторію: бекендові пункти закриті в `app/Services/PromoService.php` (гравець з токена, транзакція з локом, ledger, integer-центи, ідемпотентність через унікальний індекс, доменні винятки з чесними HTTP-кодами) плюс схема БД і feature-тести; фронтендові — у Vue-компонентах (loading/disabled-стани, try/catch з людськими повідомленнями, захист від подвійного кліку).
