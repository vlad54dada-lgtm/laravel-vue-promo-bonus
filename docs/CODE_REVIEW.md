# Частина 2 — Рев'ю коду

Рев'ю фрагмента «нарахувати бонус на баланс гравця» (роут + `WalletController::creditBonus` + фрагмент Vue-компонента). Формат — як коментар до PR колеги.

## Загальний вердикт

У поточному вигляді це не «фіча з шорсткостями», а пряма діра для виведення грошей: **будь-хто без автентифікації може змінити баланс будь-якого гравця на довільну суму (включно з від'ємною) одним GET-запитом**. Мержити не можна; нижче — розбір за пріоритетом.

## Критичне (блокери)

**1. Мутація стану через GET.**
`Route::get('/players/{player}/credit-bonus', ...)` змінює баланс. Наслідки: GET префетчиться браузером, «відкривається» прев'ю месенджерів (бонус нарахується без жодного наміру користувача), потрапляє з усіма параметрами в access-логи та історію браузера. `<img src="https://site/api/players/1/credit-bonus?amount=100000">` на будь-якому сайті виконає операцію — уточню: не тому, що «GET обходить CSRF» (CSRF-middleware Laravel на API-роути не поширюється взагалі, ані на GET, ані на POST — `ValidateCsrfToken` є лише у web-групі), а тому, що ендпоінт відкритий без автентифікації (п. 2). Перехід на `POST` потрібен за семантикою HTTP і прибирає вектори prefetch/прев'ю/логів, але сам по собі захисту не додає — від cross-site запитів тут захищає Bearer-автентифікація (Sanctum), токен якої браузер не відправляє автоматично. Кешування відповіді малоймовірне (Laravel за замовчуванням віддає `Cache-Control: no-cache, private`), але покладатися на дефолтний заголовок для грошової операції не можна.

**2. Немає ані автентифікації, ані авторизації.**
Роут не під `auth`-middleware, тобто доступний аноніму. Гравець береться з URL (`{player}`), а не з токена — класичний IDOR: перебором `player_id` можна нарахувати (або з мінусом — списати, див. п. 3) кошти будь-кому. За вимогами домену гравець має визначатися з токена автентифікації, а нарахування бонусу взагалі не повинно бути операцією, доступною самому клієнту на довільну суму — це або службова (адмінська) дія, або наслідок бізнес-події (промокод, депозит-бонус), де суму визначає сервер.

**3. `amount` не валідується взагалі — і суму диктує клієнт.**
- `amount` відсутній → `$request->amount` = `null` → `balance += null` — «успішна» операція без ефекту, 200 OK.
- Від'ємний `amount` → це вже **списання** коштів GET-запитом без жодних перевірок.
- Нечислове значення (`"abc"`) → у нестрогому режимі TypeError або тихе приведення типів залежно від версії PHP — недетермінована поведінка.
- Немає верхньої межі — `?amount=999999999` нараховує мільярд.
Навіть із валідацією залишається концептуальна помилка: сума бонусу має визначатися сервером за бізнес-правилом, а не прийматися з запиту.

**4. Race condition: read-modify-write без транзакції та блокування.**
`$player->balance += ...; $player->save()` — між читанням (route model binding) і записом інший запит може змінити баланс → lost update. Два паралельні нарахування по 100 можуть дати +100 замість +200 (втрата) або, у зв'язці з ретраями клієнта, +400 (подвоєння). Потрібно: `DB::transaction` + `lockForUpdate()` (або атомарний `increment()`), плюс **ідемпотентність** — унікальний ключ операції нарахування, щоб мережевий ретрай не нарахував бонус двічі. Для гемблінг-домену це не «nice to have», а основна вимога.

**5. Гроші через float-арифметику.**
`balance += $request->amount` — `$request->amount` це рядок з HTTP; після приведення отримуємо float зі стандартними помилками подвійної точності (0.1 + 0.2). Баланс має зберігатися в integer мінорних одиницях (центах) або оброблятися через decimal/bcmath — але не через `+=` з сирим інпутом.

## Серйозне

**6. Витік фінансових даних: баланс будь-якого гравця читається будь-ким.**
Відповідь завжди містить `balance`, а `amount` необов'язковий (`+= null` нічого не змінює) — отже `GET /api/players/{id}/credit-bonus` без параметрів працює як неавтентифікований read-oracle поточного балансу довільного гравця (перебором id). Навіть якби мутацію заборонили, витік лишився б. Баланс має бачити лише сам гравець через автентифікований ендпоінт (`GET /api/me`).

**7. Немає журналу операцій (ledger).**
Баланс змінюється «в лоб», без запису хто/коли/за що/скільки. Неможливо аудитувати, звіряти, розслідувати інцидент чи скасувати помилкове нарахування. Для платформи з реальними грошима зміна балансу без ledger-запису — недопустима.

**8. Немає обробки помилок і статусів відповіді.**
Відповідь завжди `200 {success: true}` — навіть якби валідація була, контракт не передбачає ані 422, ані 4xx для доменних відмов. `save()` може повернути false / кинути виняток — не обробляється.

**9. Немає rate limiting** — нарахування можна викликати в циклі без обмежень.

**10. Архітектурно: логіка в контролері.**
Немає FormRequest, немає сервісного шару, `$request->amount` замість `$request->validated()`. Для грошової операції — мінімум сервіс + типізовані доменні помилки.

## Фронтенд

**11. `axios.get` з `params` для грошової мутації** — дзеркалить проблему № 1; після виправлення бекенда має стати `axios.post` з тілом.

**12. `this.player.id` у URL** — клієнт сам каже, кому нараховувати; після виправлення № 2 ідентифікатор гравця з фронтенда взагалі зникає (сервер бере його з токена).

**13. Немає обробки помилок і стану завантаження.**
`await` без `try/catch` — відхилений проміс упаде необробленим, користувач не побачить причину. Немає прапорця loading/disabled — подвійний клік = подвійний запит = подвійне нарахування (у зв'язці з № 4). Баланс перезаписується відповіддю без урахування, що запит міг задублюватися.

## Дрібніше

- Route model binding `{player}` без scoping — 404/200 дозволяє перебором зʼясовувати, які player_id існують (enumeration).
- Назва `creditBonus` у `WalletController` натякає, що поруч з'являться інші грошові операції — тим більше потрібен сервіс/ledger, а не інкремент поля в контролері.

## Як мав би виглядати підхід (ескіз)

```php
// POST /api/bonus/claim  (auth:sanctum, throttle)
public function claim(ClaimBonusRequest $request, BonusService $service)
{
    // гравець — тільки з токена; суму визначає сервер за бізнес-правилом
    $result = $service->credit($request->user(), $request->validated('reason_id'));
    return BonusResource::make($result); // 422/409 — через доменні винятки
}

// BonusService::credit — DB::transaction + lockForUpdate + унікальний
// ключ ідемпотентності + запис у wallet_transactions (integer-центи)
```
