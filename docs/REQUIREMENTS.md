# REQUIREMENTS — детальні вимоги

Джерело: [TASK.md](TASK.md). Тут — вимоги, розгорнуті до рівня, за яким можна писати код і тести без додаткових уточнень.

## Загальні правила (обидва тікети)

- **Гравець = автентифікований користувач.** Визначається виключно з Bearer-токена (Sanctum). Тіло запиту та URL ніколи не містять ідентифікатор гравця.
- **Гроші — integer у мінорних одиницях** (`*_cents`). API віддає суми в центах; фронтенд форматує для відображення. Float не використовується ніде.
- **Кожна зміна балансу — атомарна** (транзакція БД) і залишає запис у ledger (`wallet_transactions`).
- **Формат помилок API** (крім стандартної 422-валідації Laravel):

```json
{ "message": "Людиночитане пояснення", "error_code": "MACHINE_READABLE_CODE" }
```

  Окремі помилки можуть нести додаткові машинні поля поряд з `message`/`error_code` (наприклад, `next_claim_available_at` для `PROMO_COOLDOWN`).

- Неавтентифікований запит до будь-якого promo-ендпоінта → `401`.

## Контракт помилок

| HTTP | error_code | Коли |
|---|---|---|
| 422 | — (стандартний формат Laravel `errors.code[]`) | Код відсутній, коротший 6 / довший 12 символів, містить не латинські літери/цифри |
| 404 | `PROMO_NOT_FOUND` | Код валідний за форматом, але не існує в БД |
| 409 | `PROMO_EXPIRED` | Код існує, але `expires_at` у минулому |
| 409 | `PROMO_ALREADY_USED` | Цей гравець уже застосовував цей код (включно з випадком, коли нарахування потім скасували — див. рішення D3) |
| 409 | `PROMO_COOLDOWN` | Гравець уже отримав бонус за **будь-який** код протягом останніх 24 годин (рішення D7). Відповідь додатково містить `next_claim_available_at` (ISO 8601) |
| 404 | `CLAIM_NOT_FOUND` | claimId не існує **або належить іншому гравцю** (не розкриваємо існування чужих записів) |
| 409 | `CLAIM_ALREADY_REVOKED` | Повторний revoke уже скасованого нарахування |
| 409 | `CLAIM_NOT_REVOCABLE` | Спроба revoke запису зі статусом `rejected` (нічого не нараховувалось — нічого скасовувати) |

Обґрунтування: ТЗ вимагає, щоб доменні відмови були «окремою помилкою» від 422-валідації формату. 404 — ресурс не знайдено; 409 Conflict — запит суперечить поточному стану ресурсу. Кожна відповідь містить `error_code` для машинної обробки і `message` для показу користувачу.

## Ключові доменні рішення (Decisions)

- **D1. Регістр коду.** Коди зберігаються в uppercase; введення нормалізується (`summer100` ≡ `SUMMER100`) до валідації існування. Формат-валідація приймає обидва регістри.
- **D2. Відхилені спроби зберігаються.** Фільтр історії «успішно застосовано / відхилено» з ТЗ означає, що невдалі спроби (не існує / прострочений / вже використаний) **персистяться** зі статусом `rejected` і причиною. 422-помилки формату в історію **не** пишуться (запит не пройшов навіть валідацію входу).
- **D3. Повторний claim після revoke заборонено.** «Ще не був використаний цим гравцем раніше» трактуємо строго: код вважається використаним, навіть якщо нарахування пізніше скасували. Це закриває цикл зловживання claim→revoke→claim. Альтернатива (дозволити повторний claim після revoke) зафіксована як свідомо відхилена.
- **D4. Сума бонусу визначається промокодом** (`promo_codes.amount_cents`), ніколи клієнтом.
- **D5. Revoke списує рівно суму нарахування.** Оскільки в системі немає інших списань, баланс не може стати від'ємним (баланс = сума активних нарахувань). Основний інваріант — guard у коді сервісу + тести; `unsigned` у міграції діє лише на MySQL (SQLite ігнорує), додатково під MySQL — raw CHECK-констрейнт `balance_cents >= 0` (SQLite не підтримує ADD CONSTRAINT, там захист повністю програмний). У реальній системі зі ставками потрібна була б окрема політика (bonus wagering) — фіксуємо як відоме спрощення.
- **D6. Revoke доступний самому гравцю** для власних нарахувань (у реальній системі це радше адмін-операція; тут фронтенд ТЗ явно вимагає кнопку в історії гравця).
- **D7. Кулдаун: один успішний claim на 24 години на гравця** — незалежно від того, який це код. Деталі правила:
  - **Ідентифікація гравця — виключно `users.id` з Bearer-токена (Sanctum)**, як і всюди в системі. Не IP (кілька гравців за одним NAT блокували б одне одного, обхід через VPN тривіальний) і не fingerprint пристрою (не переживає інкогніто/зміну браузера; легітимний гравець з двох пристроїв — той самий гравець). Кулдаун «їздить» за акаунтом.
  - **Вікно ковзне**: 24 години від `created_at` останнього «споживаючого» claim (`applied` або `revoked`), не календарна доба.
  - **Кулдаун запускає тільки успішне нарахування.** Відхилені спроби (`rejected` будь-якої причини, включно з самим `cooldown`) його не запускають і не подовжують.
  - **Revoke не знімає кулдаун**: факт використання у вікні був (та сама логіка анти-абузу, що й у D3).
  - **Пріоритет помилок**: повторний той самий код → `PROMO_ALREADY_USED` (точніша, постійна причина); `PROMO_COOLDOWN` — лише коли сам код ще доступний гравцю. Перевірки існування/строку коду (404/`PROMO_EXPIRED`) теж ідуть раніше за кулдаун.
  - Відхилена через кулдаун спроба персистується в історію: `rejected` / `cooldown`.
  - Довжина вікна — конфіг `promo.cooldown_hours` (env `PROMO_COOLDOWN_HOURS`, дефолт 24), не магічне число.

## Тікет 1 — Backend

### POST `/api/promo/claim`

Вхід: `{ "code": "SUMMER100" }`. Правила валідації: `required|string|regex:/^[A-Za-z0-9]{6,12}$/`.

Успіх `200`:

```json
{
  "bonus_amount_cents": 10000,
  "balance_cents": 10000,
  "claim": { "id": 1, "code": "SUMMER100", "status": "applied", "amount_cents": 10000, "created_at": "..." }
}
```

Послідовність (кроки 3–4 — в одній транзакції; rejected-запис при відмові — окрема операція, див. примітку):
1. Нормалізувати код (uppercase), знайти промокод → ні: записати `rejected/not_found`, віддати 404.
2. Прострочений → записати `rejected/expired`, віддати 409.
3. У транзакції: `lockForUpdate` рядка гравця; перевірити відсутність claim зі статусом `applied|revoked` для (гравець, код) — **обов'язково locking read'ом** (`...->lockForUpdate()->exists()`): звичайний SELECT під InnoDB REPEATABLE READ читає снапшот транзакції і не побачить щойно закомічений паралельний claim. Є → записати `rejected/already_used`, віддати 409.
4. Там само в транзакції: кулдаун D7 — locking read'ом знайти останній «споживаючий» claim гравця (`promo_code_id IS NOT NULL`) за останні 24 години. Є → записати `rejected/cooldown`, віддати 409 з `next_claim_available_at = created_at + 24h`.
5. Створити claim `applied`, збільшити баланс, записати ledger-рядок, віддати 200.
6. Другий рубіж: унікальний індекс на (user_id, promo_code_id); порушення при гонці → відповідь як `PROMO_ALREADY_USED`.

Примітка: rejected-записи створюються **поза** транзакцією нарахування — при відмові нарахування немає (транзакція відкочується або не відкривається), і якби rejected-запис був її частиною, він відкотився б разом з нею.

### GET `/api/promo/history`

Параметри: `status` (optional: `applied` | `rejected` | `revoked`), `page`, `per_page` (default 10, max 50). Сортування: новіші перші. Тільки claim'и поточного гравця. Відповідь — стандартна пагінація Laravel (`data`, `meta`).

Кожен елемент: `id`, `code` (що вводив гравець), `status`, `reject_reason` (nullable), `amount_cents` (nullable для rejected), `created_at`, `revoked_at` (nullable).

### Rate limiting

`POST /api/promo/claim` — throttle (10 запитів/хв на користувача): захист від перебору кодів.

## Тікет 1 — Frontend

- Форма з одним полем «Промокод» + кнопка «Застосувати».
- Стани: `idle` → `loading` (кнопка disabled, спінер) → `success` (повідомлення: сума бонусу + новий баланс) / `error` (текст причини з `message` відповіді; для 422 — текст помилки валідації).
- Клієнтська валідація дублює серверну (6–12, латиниця/цифри) — але сервер лишається джерелом істини.
- Під формою — історія: дата, код, сума, статус (бейдж: applied / rejected / revoked), причина відмови для rejected.
- Фільтр за статусом (All / Applied / Rejected / Revoked) + пагінація.
- Після успішного claim історія та баланс оновлюються.
- Десь у layout видно поточний баланс гравця.

## Тікет 2 — Backend

### PATCH `/api/promo/{claimId}/revoke`

Без тіла. Послідовність (одна транзакція):
1. `lockForUpdate` рядка поточного гравця. **Єдиний порядок локів у системі: спершу рядок гравця, потім рядки promo_claims** — той самий, що й у claim; інакше claim (user→claim) і revoke (claim→user) утворюють класичний deadlock під MySQL.
2. Знайти claim за id **серед claim'ів поточного гравця**, `lockForUpdate` → ні: 404 `CLAIM_NOT_FOUND`.
3. Статус `revoked` → 409 `CLAIM_ALREADY_REVOKED` (кошти НЕ списуються вдруге — головна вимога ТЗ). Статус `rejected` → 409 `CLAIM_NOT_REVOCABLE`.
4. Статус `applied`: перевести статус **умовним UPDATE** `UPDATE promo_claims SET status='revoked', revoked_at=... WHERE id=? AND status='applied'` і перевірити affected rows — СУБД-незалежний рубіж проти подвійного списання (0 рядків → перечитати claim і віддати 409). Далі зменшити баланс на `amount_cents`, ledger-рядок зі знаком мінус.

Успіх `200`:

```json
{ "balance_cents": 0, "claim": { "id": 1, "status": "revoked", "revoked_at": "..." } }
```

## Тікет 2 — Frontend

- Кнопка «Скасувати» тільки біля записів зі статусом `applied`.
- Клік → підтвердження (модалка/confirm: «Скасувати бонус X за кодом Y? Сума буде знята з балансу»).
- Під час запиту — кнопка конкретного рядка в loading/disabled (подвійний клік неможливий).
- Після успіху: статус рядка → `revoked`, баланс оновлено, коротке повідомлення.
- Помилка (напр., вже скасовано в іншій вкладці) → показати `message`, оновити список.

### Claim

| # | Сценарій | Очікування |
|---|---|---|
| C1 | Валідний код, перший раз | 200, баланс +amount, claim `applied`, ledger-рядок |
| C2 | Код відсутній / 5 симв. / 13 симв. / `промо!@#` | 422, в історію НЕ пишеться |
| C3 | Неіснуючий код правильного формату | 404 `PROMO_NOT_FOUND`, історія: rejected/not_found |
| C4 | Прострочений код | 409 `PROMO_EXPIRED`, історія: rejected/expired |
| C5 | Повторний claim того самого коду | 409 `PROMO_ALREADY_USED`, історія: rejected/already_used, баланс не змінився |
| C6 | Claim коду, нарахування за яким скасовано | 409 `PROMO_ALREADY_USED` (рішення D3) |
| C7 | Той самий код у lowercase | Працює як C1/C5 (нормалізація, D1) |
| C8 | Два паралельні claim одного коду | Рівно одне нарахування; другий запит 409 (лок + унікальний індекс) |
| C9 | Без токена | 401 |
| C10 | Інший гравець застосовує той самий код | 200 — код одноразовий **на гравця**, не глобально |
| C11 | Інший код у межах 24 год після успішного claim | 409 `PROMO_COOLDOWN` + `next_claim_available_at`, історія: rejected/cooldown, баланс не змінився |
| C12 | Інший код через 24+ год після успішного claim | 200 (вікно ковзне і спливло) |
| C13 | Rejected-спроби не запускають і не подовжують кулдаун | Невдала спроба (not_found або cooldown) → наступний claim по тому самому вікну від **успішного** claim |
| C14 | Інший код у межах 24 год після claim → revoke | 409 `PROMO_COOLDOWN` — revoke не знімає кулдаун (D7) |
| C15 | Кулдаун — на гравця: другий гравець claim'ить у «чужому» вікні | 200 — вікна незалежні (ідентифікація за `users.id` з токена) |
