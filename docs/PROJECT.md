# PROJECT — Promo Bonus Mini-Platform

Огляд проєкту для тестового завдання «AI-асистований розробник (Laravel/Vue)». Повний текст ТЗ — у [TASK.md](TASK.md).

## Суть

Міні-фіча гемблінг-платформи: гравець вводить промокод → отримує бонус на баланс; бачить історію застосувань; помилково нарахований бонус можна скасувати. Ключова цінність — **не** «просто працює», а **коректність грошових операцій**: жодного подвійного нарахування, жодного подвійного списання, жодних від'ємних сум, повний аудит-слід кожної зміни балансу.

## Що є мірилом якості (з ТЗ, прямим текстом)

1. Захист від зловживань: подвійне нарахування (повторний claim, паралельні запити, ретраї), подвійне списання (повторний revoke).
2. Від'ємні суми неможливі.
3. Гравець визначається **тільки з токена автентифікації** — ніколи з тіла запиту чи URL.
4. Чіткий контракт помилок: 422 для невалідного формату; окремі, зрозумілі помилки для «не існує / прострочений / вже використаний».
5. Реальна історія комітів (розбита за етапами, не один фінальний коміт).

## Межі скоупу (що ми свідомо НЕ робимо)

- Реєстрація користувачів, відновлення пароля — тільки мінімальний login для демо (гравець сідиться).
- Адмін-панель керування промокодами — коди сідяться.
- Ліміт використань коду глобально (max_uses) — поза ТЗ; фіксуємо як «відоме розширення».
- Реальні гроші/платіжки, мультивалютність — одна умовна валюта, суми в мінорних одиницях (центах).
- Складний UI/дизайн — фронтенд акуратний, але мінімальний: форма + історія + скасування.

ТЗ дає орієнтир 4–6 годин. Розбивка за етапами — у [ROADMAP.md](ROADMAP.md). Принцип: спершу коректний бекенд із тестами (це те, що оцінюють найприскіпливіше), потім фронтенд, потім полірування.

## Ключові ризики та як їх закриваємо

| Ризик | Захист |
|---|---|
| Подвійне нарахування (паралельні claim) | Транзакція + `lockForUpdate` + унікальний індекс як другий рубіж |
| Подвійне списання (повторний revoke) | Транзакція + lock рядка claim + перевірка статусу `applied` → 409 |
| Від'ємний баланс | Єдине джерело списань — revoke раніше нарахованого; guard у сервісі + тести (+ CHECK `balance_cents >= 0` під MySQL; SQLite не підтримує ADD CONSTRAINT) |
| Гроші у float | Всі суми — integer у мінорних одиницях (центах), ніяких float |
| Втрата аудит-сліду | Таблиця `wallet_transactions` (ledger) на кожну зміну балансу |
| Підміна гравця | Гравець тільки з `auth()->user()`, claim'и фільтруються за власником |
