Результат: AI прочитав PDF, виділив ключові акценти ТЗ (коректність грошових операцій, захист від подвійного нарахування/списання, гравець тільки з токена, окремий контракт помилок, реальна історія комітів) і створив пакет документів: `TASK.md`, `PROJECT.md`, `REQUIREMENTS.md` (з матрицею крайніх випадків), `ARCHITECTURE.md` (схема БД, стратегія конкурентності), `ROADMAP.md` (етапи + план комітів), чернетку `CODE_REVIEW.md` (Частина 2), цей лог.

Ключові рішення, запропоновані AI на цьому кроці (зафіксовані в REQUIREMENTS/ARCHITECTURE):
- гроші тільки в integer-центах;
- rejected-спроби персистяться (бо ТЗ вимагає фільтр історії «відхилено»);
- `promo_code_id` NULL для rejected-записів → простий UNIQUE(user_id, promo_code_id) працює і в MySQL, і в SQLite;
- транзакція + `lockForUpdate` + унікальний індекс як три рубежі проти подвійного нарахування;
- повторний claim після revoke заборонений (анти-абуз циклу claim→revoke→claim);
- append-only ledger `wallet_transactions` для аудиту кожної зміни балансу.

Ітерації: чернетки документів прогнано через адверсарну AI-верифікацію (3 незалежні агенти: повнота проти тексту ТЗ / технічна коректність архітектури / фактчек код-ревью). Знайдено 12 проблем (4 суттєві), усі виправлено. Найважливіші:
- твердження «на SQLite гонки неможливі фізично» було хибним — другий конкурентний писатель отримує `SQLITE_BUSY` (500, а не контрактний 409); додано СУБД-незалежні рубежі: для claim — унікальний індекс, для revoke — умовний UPDATE з перевіркою affected rows;
- перевірка «код уже використаний» звичайним SELECT під InnoDB REPEATABLE READ читала б застарілий снапшот — виправлено на locking read (`lockForUpdate`);
- порядок локів у claim (user→claim) і revoke (claim→user) був різним — класичний deadlock; зафіксовано єдиний порядок «спершу гравець, потім claim»;
- у чернетці код-ревью (Частина 2) була фактична помилка про CSRF: на API-роути Laravel CSRF-middleware не поширюється взагалі, тож перехід на POST сам по собі захисту не додає — переписано; додано пропущений пункт про неавтентифікований read-oracle балансу.

## Етап 1 — Схема БД і сідери

Виконано за планом з ARCHITECTURE.md без окремих промптів (детальний дизайн схеми зафіксовано на етапі аналізу). Створено: міграції (balance_cents у users, promo_codes, promo_claims з UNIQUE(user_id, promo_code_id), wallet_transactions як append-only ledger), string-backed PHP-енуми статусів, моделі, фабрику PromoCode, сідер з демо-гравцями та трьома кодами.

Ітерація під час реалізації: у документах було заявлено CHECK `balance_cents >= 0` «при створенні таблиці», але колонка додається через ALTER до існуючої таблиці users, а SQLite не підтримує `ALTER TABLE ... ADD CONSTRAINT` — CHECK лишено тільки під MySQL (driver-умовно), документацію синхронізовано з реальністю. `balance_cents` свідомо не у `$fillable` — захист грошового поля від масового присвоєння.
